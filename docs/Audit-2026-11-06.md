Архитектура имеет полезные границы: отдельный координатор inspect, разделение
сбора/оценки/представления экипировки, единый core профилей, контроллер черновиков,

оснований нет. Главные задачи — исправить оставшийся после перехода bootstrap,
ограничить стоимость журнала профиля и укрепить границу чтения SavedVariables.

`npm run check` прошёл: TypeScript и **77/77 тестов**, внутри набора — **156 Lua
rule checks**. Это не доказывает отсутствие ошибок: дополнительные пробы выявили
случаи, отсутствующие в штатных тестах. Критических дефектов P0 в проверенном
объёме не подтверждено. Проверки в настоящем WoW в этот аудит не входят.

Приоритеты: P1 — существенная деградация или риск неверных данных;
P2 — обычная ошибка/важный пробел надёжности; P3 — ограниченный крайний случай
или сопровождение. Приоритет не означает, что проблема воспроизводится у всех.

## Подтверждённые проблемы

### F01 · P2 · Ложная ошибка модуля рейтингов при нормальном запуске

**Источник:** `Raidwise/Raidwise.lua:276–278`, `Raidwise/PlayerHistory.lua:443`, TOC.

`OnInitialize` проверяет `self.RatingTagGroups`, хотя определение осталось только
в отключённом `PlayerHistory.lua`. Ни один из 50 активных модулей его не задаёт.
При нормальной загрузке выводится `Player rating module failed to load. Update
PlayerHistory.lua and /reload.` — даже когда новый core исправен.

**Доказательство:** вызов настоящего `OnInitialize` с минимальными API-заглушками
вывел эту ошибку и затем обычное сообщение о загрузке v2.0.0. Статический проход
по TOC нашёл ноль активных определений проверяемого метода.

**Исправление:** проверять контракт активного core/bridge и заменить совет о
переустановке retired-файла. Добавить загрузочный тест именно активного TOC,
проверяющий отсутствие ложного сообщения при валидной БД.

### F02 · P1 · Квадратичный рост журнала событий профиля

**Источник:** `Raidwise/PlayerRecords.lua:255–269`, `:86–89`;
`Raidwise/ProfileWindow.lua:93`, `Raidwise/PlayerEncounters.lua:60–76`.

Каждое изменение массива событий сохраняет в `changes` полные копии `before`
и `after`. При последовательном добавлении и сохранении N событий журнал хранит
N² копий событий. `PruneHistory` очищает встречи, но не этот журнал. Чтение
`GetPlayerRecord` глубоко копирует весь журнал, включая вложенные snapshots;
открытие/обновление профиля оплачивает эту стоимость.

**Доказательство:** 100 добавлений через реальные `AddPlayerRecordDraftEvent` и
`CommitPlayerRecordDraft` дали 100 текущих событий и **10 000** экземпляров событий
в `changes.before/after`. Это измеренное число объектов, не измерение FPS или RAM.

**Последствие:** рост SavedVariables и стоимости сохранения/отрисовки одного
активно используемого профиля; пагинация UI не ограничивает объём копируемых данных.

**Исправление:** журналировать добавление/удаление/изменение по event ID; возвращать
отдельно профиль и страницу журнала. Миграцию существующего журнала делать
версионированной, с сохранением пользовательской истории. Приёмка: нагрузочные
фикстуры 100/1 000 событий, линейный объём журнала, прежняя авторизация и stale-draft
защита, сохранность старых записей.

### F03 · P2 · Вложенная повреждённая запись проходит проверку БД и падает при чтении

**Источник:** `Raidwise/PlayerRecords.lua:60–74`, `:92–97`;
`Raidwise/PlayerRecordBridge.lua:21–24`.

`InitializePlayerRecords` проверяет таблицы разделов и `nextId`, но не форму
профилей/заметок/встреч. `GetPlayerRecordStore` проверяет только номер схемы.
В корректном контейнере запись `profiles.X = {}` принимается и затем приводит к
`attempt to get length of field 'facts' (a nil value)` в `IsPlayerRecordFilled`.
На этом пути строится База персонажей.

**Условие:** повреждённые, вручную изменённые или частично записанные старым кодом
данные. Штатное создание профиля текущим core такую запись не производит;
самопроизвольная порча данных не доказана.

**Исправление:** валидировать вложенные записи на границе загрузки; изолировать
некорректную запись с диагностикой и возможностью восстановления, не очищая
автоматически пользовательскую БД. Неизвестную схему сохранять. Тесты: неверные
типы facts/events/note/encounter, отсутствующие поля, независимость здоровых записей.

### F04 · P3 · JSON-экранирование неполно для управляющих символов

**Источник:** `Raidwise/CharacterExport.lua:29–36`,
`Raidwise/CharacterLockouts.lua:484–491`.

Оба `JsonEscape` экранируют кавычку, backslash, LF/CR/TAB, но оставляют другие
символы U+0000–U+001F. Проба реального `FormatEquippedGearExport` с именем предмета
`item .. string.char(1) .. name` дала JSON, отвергнутый `JSON.parse`.

**Условие:** необычные строки API/сохранений, например кастомный сервер;
наличие таких строк в обычных игровых данных не подтверждено. Это дефект границы
сериализации, не утверждение, что обычный экспорт сейчас сломан.

**Исправление:** общий JSON string encoder с `\u00XX` для оставшихся control chars;
проверить все 32 кода, кавычки, backslash и кириллицу через реальный JSON parser.

## Условный риск корректности данных

### R01 · P1 при совпадении GUID между реалмами · Ключ идентичности не включает realm

**Источник:** `Raidwise/PlayerRecords.lua:116–160`,
`Raidwise/GearCheckSavedReports.lua:45–61`,
`Raidwise/RatingPresentation.lua:62–70`.

Имя без GUID получает ключ с realm, но известный GUID используется самостоятельно.
Если две серверные среды возвращают один GUID разным персонажам, второй upsert
перезаписывает identity, сохраняя прежнее мнение/заметку по тому же ключу.
Синтетическая проба `X/Alice/RealmA → X/Bob/RealmB` сохранила Bob чужое `negative`.

**Статус:** реакция кода доказана; наличие такой коллизии на серверах пользователя
не установлено. Это не подтверждённый инцидент потери данных. До изменения схемы
уточнить поддерживаемую область уникальности GUID. Если допускаются независимые
реалмы с пересечением GUID — ввести namespace realm/server, конфликт-детектор и
миграцию всех ссылок (observer/subject, groups, drafts, reports), а не просто
поменять одну функцию ключа. КД уже используют отдельную модель name/realm.

## Что работает и что сохранять при исправлениях

- Inspect имеет одного владельца, проверяет текущую identity unit token,
  поддерживает unit/GUID payload, завершение и отмену; есть отдельные lifecycle tests.
- Canonical report adapter сохраняет legacy aliases, отделяет completeness от grade.
- Core отклоняет stale drafts, защищает самооценку и авторство событий; deletion
  использует generations. Ошибочные черновики сохраняются в памяти редактора.
- Profile exchange отключён в TOC и bridge. Поиск `SendAddonMessage` и
  `CHAT_MSG_ADDON` обнаружил транспорт только в retired `SyncTransport.lua`.
  Это не независимый аудит всех возможных каналов передачи данных.
- Roster refresh объединяет запросы и разделяет snapshot между потребителями;
  скрытые raid/composition views не перерисовываются этим обработчиком.
- Release validator проверяет tag, две addon-версии и наличие changelog;
  release workflow выполняет `npm run check` перед упаковкой.
- Тесты исполняют настоящий Lua 5.1 через WASM; 50 активных модулей проходят
  компиляцию. Моки не заменяют WoW API и визуальную проверку.
