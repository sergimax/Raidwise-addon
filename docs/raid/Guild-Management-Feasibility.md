# Управление гильдией из Raidwise: оценка реализуемости

Дата: 2026-11-16. Цель: WoW 3.3.5a, Interface 30300. Это исследование, не реализованная функция. Проверка в целевом клиенте и на сервере ещё не выполнялась.

## Вывод и API

Все запрошенные действия доступны для реализации собственным интерфейсом аддона в пределах прав персонажа. Основание — исходники штатного интерфейса 3.3.5, опубликованные в зеркале:

- [FriendsFrame.lua](https://github.com/wowgaming/3.3.5-interface-files/blob/main/FriendsFrame.lua): `GetNumGuildMembers`, `GetGuildRosterInfo`, `GuildRoster`, `GUILD_ROSTER_UPDATE`; отдельные проверки `CanViewOfficerNote`, `CanEditPublicNote`, `CanEditOfficerNote`, `CanGuildPromote`, `CanGuildDemote`. В `GuildFrame_Update` повышение/понижение дополнительно ограничены иерархией званий.
- [FriendsFrame.xml](https://github.com/wowgaming/3.3.5-interface-files/blob/main/FriendsFrame.xml): кнопки вызывают `GuildPromote(name)` и `GuildDemote(name)`; журнал запрашивается через `QueryGuildEventLog`, ответ обрабатывается по `GUILD_EVENT_LOG_UPDATE`.
- `GuildEventLog_Update` в указанном Lua читает `GetNumGuildEvents` / `GetGuildEventInfo`: приглашение, вступление, повышение, понижение, исключение, выход. Истории редактирования заметок этот обработчик не предоставляет.

Запись заметок подтверждена в [StaticPopup.lua](https://github.com/wowgaming/3.3.5-interface-files/blob/main/StaticPopup.lua#L1997-L2060): `GuildRosterSetPublicNote(index, text)` и `GuildRosterSetOfficerNote(index, text)`. Штатные редакторы используют `maxLetters = 31`; это ограничение интерфейса, а не доказанный серверный лимит байтов. Чтение офицерской заметки и право её изменения — разные разрешения.

## Что уже есть в репозитории

- `Raidwise_EPGP/GuildRosterExport.lua`: получение имён, классов, званий, двух заметок; запрос обновления и включение офлайн-персонажей.
- `Raidwise_EPGP/PageEPGP.lua`: таблица, ручное обновление, поиск по имени, публичной заметке и первой разобранной специализации. Поиск также добавляет связанных персонажей; это поведение не подходит для строгого фильтра состава без отдельного решения.
- `Raidwise/Raidwise.lua`: обработка `GUILD_ROSTER_UPDATE`, запуск ожидающих экспорта и сбора EPGP.
- Модуль EPGP загружается по требованию, отдельно от основного аддона. Путь владельца в `docs/Architecture.md` устарел: фактическая папка — `Raidwise_EPGP/`.
- Получение офицерских заметок сейчас ошибочно использует `CanEditOfficerNote` как признак доступности чтения. Это нужно исправить при реализации. Недоступная заметка должна отличаться от пустой.
- В проверенных модулях нет записи заметок, повышения/понижения и гильдейского журнала. Существующие исправления импортированного снимка не означают запись в игру; см. [EPGP-Plan.md](EPGP-Plan.md).

## Предлагаемая реализация

Отдельная страница «Состав гильдии» в разделе гильдии: имя, класс, звание, онлайн, заметка, офицерская заметка. Поиск по выбранным текстовым полям плюс фильтр класса; фильтры совместимы. Для русского поиска нужен проверенный на клиенте регистронезависимый поиск UTF-8: обычного Lua `string.lower` недостаточно считать универсальным решением.

Выбранный персонаж открывает редактор двух заметок и действия со званием. Перед записью заново искать актуальный индекс по имени в свежем составе: индекс строки таблицы после сортировки не является индексом игрового состава. Сравнивать исходное значение с текущим, сообщать о конфликте; не затирать чужую правку автоматически. Отправленную команду считать ожидающей до проверки обновлённого состава; при тайм-ауте показывать неопределённый результат, а не успех. Ограничения длины проверить в целевом клиенте.

Ручная кнопка и автоматический режим используют один сборщик: запрос при открытии, обработка событий, объединение повторных запросов, ограниченная частота, тайм-аут. При необходимости добавить настраиваемый периодический запрос, например раз в 30–60 секунд при открытой странице; это предложение, не установленный лимит API. Не вызывать запрос безусловно из каждого события обновления. Не терять несохранённый текст редактора. Общий переключатель офлайн-состава координировать со штатным окном и EPGP.

## Журнал и его ограничения

Предлагается объединить два явно обозначенных источника:

1. Доступные серверные события гильдии, сохраняемые локально с защитой от повторного импорта. Нельзя обещать безошибочное устранение дублей по уникальному ID, пока его наличие не подтверждено.
2. Наблюдаемые изменения заметок/званий между полными снимками и подтверждённые действия пользователя в Raidwise. Для внешней правки заметки автор и точное время могут быть неизвестны; время обнаружения хранить отдельно. Несколько промежуточных правок между снимками восстановить нельзя.

Хранить последние N записей в SavedVariables; N настраивается, старые записи удаляются первыми. Разделять гильдии и серверы, не смешивать с журналами профилей персонажей. Запрет чтения офицерских заметок должен распространяться и на поиск/отображение сохранённой истории.

Локальный лимит не увеличивает глубину серверной истории. Пока клиент выключен, аддон не наблюдает изменения; позже можно получить только доступную серверу историю и конечные значения заметок. Архив изначально локален для установки аддона; общий журнал офицеров потребует отдельной синхронизации. Сохранность после аварийного завершения клиента не гарантируется.

## Проверка перед выпуском

В клиенте: обычный участник, чтение офицерских заметок без редактирования, офицер и глава; офлайн-участники; ограничения званий; изменение другим офицером; конфликт редактора; потеря прав; смена гильдии; задержка ответа; повторные серверные события; сохранение и обрезка журнала после перезапуска. Точный объём серверной истории и поведение событий зависят от целевого сервера и требуют проверки.

При реализации добавить поведенческие тесты сборщика, поиска, проверки прав и адресата записи, конфликтов и лимита истории; выполнить `npm run check`. Новые страницы/геометрия потребуют layout version и обновления UI-документации по AGENTS.md. Семантическую версию без отдельного запроса не менять.
